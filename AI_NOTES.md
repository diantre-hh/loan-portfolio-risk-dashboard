# Где ИИ ошибся и что я исправил

Работал с Claude Code: он писал черновики SQL, спек и скриптов, я ставил задачи, читал код и сверял цифры. Правила, которые появились по ходу, записаны в [CLAUDE.md](CLAUDE.md)

## 1. Доля топ-10 групп считалась от суммы топ-10, а не от портфеля

В первой версии `reporting.v_top_groups` доля группы считалась оконной функцией `group_kzt / sum(group_kzt) OVER (...)` в том же SELECT, где стоял `WHERE rn <= 10`. Окно считается после WHERE, поэтому знаменатель — сумма только десяти групп, и доли в сумме давали ровно 100%. На глаз график выглядел нормально, заметил при чтении кода: доля G0004 получилась бы около 25% вместо 4,3%

Исправил: доля считается во внутреннем подзапросе до фильтра. Правило «долю от портфеля считать до `rn <= 10`» добавил в CLAUDE.md

## 2. Вьюха с переходами между срезами работала больше двух минут

Для поиска аномалий ИИ написал JOIN среза на предыдущий срез через коррелированный подзапрос `prev.report_date = (SELECT max(...) FROM v_loan_snapshot ...)`. На 4 000 строк это пересчитывало всю витрину (с LATERAL-джойном курсов) для каждой строки, прогон не уложился в 2 минуты

Исправил: `lag()` по кредиту плюс `dense_rank()` по датам, чтобы сравнивать только соседние срезы. Теперь весь пайплайн — доли секунды

## 3. CREATE OR REPLACE VIEW не прошёл после переписывания

После правки п.2 тип колонки `prev_principal` поменялся с `numeric(20,2)` на `numeric`, и `CREATE OR REPLACE VIEW` упал: Postgres не даёт менять типы колонок существующей вьюхи. ИИ этого не учёл, хотя «идемпотентность» была в задаче. Удалил вьюху один раз руками, перезапустил пайплайн дважды. В CLAUDE.md записал: при смене набора или типов колонок — осознанный `DROP VIEW ... CASCADE`, а после изменений всегда два прогона подряд

## 4. Сверки проходили, а вывод был бы неверным

Все проверки в `v_checks` были зелёными, метрики показывали «улучшение» PAR90 и NPL почти на 2 п.п. — самый очевидный вывод для комитета был «качество портфеля улучшилось». Сверки ловят ошибки расчёта, но не ошибки в источнике. Меня смутило, что PAR90 упал так сильно за один месяц. Посмотрел матрицу переходов по корзинам: 23 кредита вернулись из списания, 53 кредита прыгнули с 90+ дней просрочки в 0 без реструктуризации при обычном погашении основного долга. Без них PAR90 не падает, а растёт до 7,0%. Отсюда появились `v_dq_transitions`, `v_dq_sensitivity` и первый вывод в README

## 5. Мелочи, которые поймал сверками

- PowerShell 5.1 по умолчанию читал CSV не в UTF-8, отрасли превращались в кракозябры. В `\copy` явно указал `ENCODING 'UTF8'`, для psql — `PGCLIENTENCODING=UTF8`
- В первой версии `v_kpi` был лишний `CROSS JOIN LATERAL` только ради даты — убрал
- В черновике README цифры были чуть неточными (доля погашения у «вылеченных» кредитов, сравнение крупнейшей группы с PAR90) — переписал по результатам запросов, а не по памяти модели

## Как проверял

Эталон по всем метрикам посчитал независимо скриптом по CSV до того, как смотреть на вьюхи. Плюс `reporting.v_checks`: каждая итоговая сумма сверяется с пересчётом из `raw`, суммы по разрезам — с портфелем. Подробнее в README, раздел «Как проверял, что цифры верны»
